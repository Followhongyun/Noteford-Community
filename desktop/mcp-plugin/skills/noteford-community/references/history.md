# 完整历史与增量

在用户要求完整历史、跨会话全面分析或持续读取新增消息时阅读。普通定点问题优先搜索和上下文，不必扫描全库。

需要完整历史时，先用 `get_history_overview` 查看当前授权会话的已索引覆盖。为避免历史遍历期间新增消息被跳过，先调用 `read_changes(start=now)` 取得临时起点，但不要标记处理完成或保存为最终检查点；再调用 `read_history`，原样传回 cursor 直到 `has_more=false`；最后从临时起点调用 `read_changes` 到 `has_more=false`，去重处理，全部成功后才保存最终增量游标。单页 limit 不超过 100；即使本页零命中，只要 `has_more=true` 仍须继续。历史顺序是稳定入库顺序，不是发送顺序。也可用 `read_changes(start=beginning)` 重放当前授权范围日志。覆盖数量只代表已索引历史，`source_total_known=false` 时不能声称微信全部历史完整。


监控新消息时使用 `read_changes`。用户若只要未来消息，可明确选择 `start=now`；需要已有历史加未来增量时必须使用上一段的临时起点衔接流程。每个连接和资料库分别保存游标；游标绑定当前有效授权范围，`all_synced` 也必须校验该范围。选择或授权范围改变及旧 `all_synced` 游标升级会返回 `cursor_reset_required`；必须显式报告并按临时起点衔接流程重做，或以 `start=beginning` 重放，不能只 `start=now`，也不能先读完历史再取 now。成功处理整页后才保存新游标，失败时用原游标重试，遵循 `has_more`，并按资料库与序号去重。删除事件或 `current=null` 没有可总结的正文。


历史或搜索返回 `cursor_reset_required` 时，索引编辑、删除、epoch 或有效授权范围可能已变化。重新验收范围并重做上述衔接流程，不能拼接不同快照后声称完整。游标是不透明值，原样传回；续页保持查询条件一致。

若客户端没有持久任务或调度能力，只完成本次读取，不承诺后台持续监控。用户要求保存检查点时，由客户端在私有任务状态中按连接和资料库保存；不改 Noteford 配置。处理删除事件时更新已有分析，不把删除事件当成新的聊天正文。
